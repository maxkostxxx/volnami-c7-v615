# C7 v613: задержка позы полного сайта

Предыдущий проход дал проверенный и опубликованный v613; это progress. В текущем проходе97/97 checkpoint SHA и пользовательский tracked diff повторно совпали. Продуктовый код пока не менялся.

## K0: установленное состояние

Очередь ограничена тремя GPU-fences, доставка свежей позы в worker не оказалась основной задержкой. За полностью непрозрачной секцией/меню новые render прекращаются. Рендеру по-прежнему не хватает запаса для стабильных60 кадров/с, но этот headless опыт **не измеряет показанные кадры**.

| Полный сайт, видимый пролёт | 1440×900 / buffer2160×1350 | 2560×1080 / buffer3840×1620 |
|---|---:|---:|
| Active submitted renders/s | 41,82 | 35,62 |
| Active main rAF/s | 52,21 | 47,37 |
| Main send → render start, p50 / p95 | 0,20 / 17,30ms | 0,10 / 24,00ms |
| CPU submission wall, среднее / p95 | 8,26 / 13,30ms | 8,53 / 14,80ms |
| Main send → observed fence completion, p50 / p95 | 65,40 / 128,30ms | 82,30 / 154,10ms |
| Новые кадры за покрытием после1s установления | 0 | 0 |
| Новые compileShader во время измеренного пролёта | 0 | 0 |

CPU submission wall включает вызовы Three/GL и возможные остановки драйвера; это не эксклюзивное GPU-время. Fence completion наблюдается существующим polling и включает очередь и задержку наблюдения. Хвосты, пересекающие границы стадий, исключены из соответствующей статистики и посчитаны отдельно в JSON. Максимальная очередь3; CPU idle не трактуется как GPU utilisation.

В покое при живых волнах было56,69/46,74 submitted/s; после возврата60,00/50,39. Фазы, камера и работа света в покое отличаются от пролёта: разницу нельзя назвать точной стоимостью одного PMREM или shadow pass. Полный сайт на этих частных запусках работает быстрее исторических v600 замеров; **это не парное сравнение версий**.

## Метод и ограничения

Один валидный запуск на каждый размер, Chromium153.0.8010.12, ANGLE Metal Apple M3 Pro, deviceDPR1, неизменный high-профиль. Настоящий production client без `c7-debug` и без его per-frame DOM JSON. Пять секунд прогрева полным пролётом,1s установки,3s воды без движения камеры,16s down/up,3s полного покрытия,3s возврата. Native scroll, easing и queue3 прежние. Worker переопределён только для скалярных timestamp/counter записей; новых GL calls, fence/poll/readback в измеряемое окно не добавлено.

В первом2560 запуске диагностический assert неверно предполагал, что services выше viewport1080. Частичный результат не сохранён и не используется;1440 сохранён. После документированного исправления повторён **только2560**, покрытие проверено через настоящее полноэкранное меню. Это ошибка протокола, не дефект сайта. `k0-harness-correction.json` сохраняет причину. Накладные расходы instrumentation не калиброваны, один запуск не задаёт доверительный интервал.

Источники: `evidence/c7-architecture-speed-2026-10-31/k0-hypothesis.json`, `k0-worker-latency.{mjs,json,log}`, `k0b-worker-latency.{mjs,json,log}`, `k0-analyze.py`, `k0-summary.json`. SHA исходного/инструментированного worker и world записаны в JSON. Основной и worker часы приведены к общей шкале через [performance.timeOrigin](https://developer.mozilla.org/en-US/docs/Web/API/Performance/timeOrigin); интерпретация статуса взята из [clientWaitSync](https://developer.mozilla.org/en-US/docs/Web/API/WebGL2RenderingContext/clientWaitSync).

Прочитаны текущие landscape.tsx, scene/render-worker.ts, worker-entry.js, scripts/c7-flight-paired.mjs, действующий fixed-packet harness и v603 queue2/queue3 результаты. Queue2 не повторяется: он ранее потерял throughput. ## K1: проверенный следующий шаг

В landscape.tsx используется `1-exp(-7.2*delta)`: намеренная постоянная времени камеры138,9ms, примерно320ms до90% шага ещё до GPU. Проверяется14,4/s —69,4ms, с той же траекторией, единым solar/camera, прежним wave clock и точным snap1e-6. Это явное изменение отзывчивости, а не удешевление одного кадра. Прежний v477 solar deadband не возвращается.

До запуска зафиксирован `k1-hypothesis.json`: ABBA, ≥25% сокращения input-to-observed90% latency, сохранение точного конечного состояния/монотонности, не более3% потери active submitted throughput. Нет перебора easing-коэффициентов при провале. G04/G07 остаютсяREWORK, G08OPEN; физические устройства/nativeSafari/residentGPUpeak/presentedFPS — NOT_RUN.

K1 прошёл: прототип1440 −39,10% задержки при −0,79% submitted throughput; дополнительные390/2560 AB-пары подтвердили точные конечные позы и отсутствие перелёта. После сборки выполнен отдельный ABBA итоговых v613/v614:442,15→277,53ms (−37,23%), throughput42,012→42,048 — без доказанного изменения. Одна строка damping перенесена в продукт и опубликована как [v614](c7-scroll-response-v614-2026-10-31.md); runtime-v613 побайтно прежний. Первый абзац этого аудита описывает состояние **до K1**, а не отсутствие последующих изменений.
