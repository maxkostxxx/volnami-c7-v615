# C7 v628 · ускорение старта (план от 04.11.2026, после v627)

Визуальных изменений НЕТ. Цель — сократить время до готовности 3D на слабой
сети (4 Мбит/с/100 мс: сейчас v625/627 ≈ 8.6 с в честном A/B, v625-док 6.3 с
своим харнессом). Три работы по убыванию выигрыша.

## Работа 1: отложить main-thread 3D fallback (кл. JS ~360 КБ)

Факт: в клиентских чанках есть ~359 КБ с three.js (0f3c8638.js) на главном
потоке. Сцена живёт в worker; полный main-thread-дубль нужен только при
недоступности worker/WebGL/offscreen. Если модуль импортируется жадно — каждый
визит качает и исполняет ~360 КБ (~0.7 с @ 4 Мбит/с).

Шаги: найти жадный импорт (app/c7/scene/*.ts, landscape.tsx) → перевести на
динамический import() внутри функции fallback → проверить, что путь worker
остался без этого чанка (request-map: чанк 359 КБ не в initial) и fallback
работает (lifecycle-тест с aborted worker).

Риск: низкий. Гейт: worker-путь без чанка; fallback готов; 0 page errors.

## Работа 2: перекрытие «второй волны» сети с CPU (0.5–1 с)

Факт (водопад 4 Мбит/с): mobile-data (sky-data 522 КБ, left-sky 270 КБ,
leaves 300 КБ, bark ~95 КБ, cloud 48 КБ ≈ 1.24 МБ) стартуют только ПОСЛЕ
завершения world.js; затем worker декодирует рельеф/поля — сеть простаивает.

Шаги: в lab worker-entry.js — fire-and-forget прогрев HTTP-кэша: прочитать
mobile-data/manifest.json (2 КБ) → fetch() каждого файла списка без декода
(результат отбросить, ошибки проглотить). Реальные потребители читают из кэша.
Десктоп-профиль подхватывается тем же списком (если манифест общий — проверить).

Риск: низкий (чистый прогрев кэша, никакой логики). Гейт: request-map —
запросы mobile-data стартуют раньше; готовность не хуже; перенос общий.

## Работа 3: zstd level max на транспорты (3–10 % байт)

Шаги: глянуть c7-bake-zstd-transports.mjs (уровень сжатия) → поднять до
максимума, измерить размеры и время декода (готовность). Оставить только если
суммарно ≥3 % без удорожания декода на телефоне (zstd декод ~одинаков).

Риск: низкий. Гейт: размеры меньше, декод не медленнее (ready A/B не хуже).

## Пакет/публикация

runtime-v628 (новый каталог) + ссылки app (render-worker, shared-world,
early-worker, build-local, page.tsx prefetch → v628) + полный конвейер → гейты
(зонная pixel-идентичность v627↔v628 на фиксированных позах: всё, кроме травы
(время) — байтово; lifecycle fallback; ready A/B 4 Мбит/с чередованием;
public: SHA, браузер, check-host, скриншоты) → деплой на ту же ссылку →
отчёт + сообщение. В визуале ничего не меняется.

## Порядок и ожидания

1. Работа 1: −360 КБ ≈ −0.7 с @ 4 Мбит/с (и минус parse на любом канале).
2. Работа 2: ≈ −0.5–1 с (перекрытие).
3. Работа 3: −100–300 КБ.
Итог @ 4 Мбит/с: 8.6 → ~6–6.8 с. На быстром канале: 2–3 → 1.6–2.2 с.
