# C7 v618: почему живая сцена появляется через четыре секунды

02.11.2026. Проверена актуальная публикация https://maxkostxxx.github.io/c7/ и изолированная копия её runtime. **Это аудит с диагностическими опытами, без изменения продукта и публикации.** 171 файл app/c7, авторской сцены и runtime совпадает с состоянием до аудита. Работа без агентов и видимых окон.

## Вывод

Загрузка ограничена не одним большим изображением. После гидратации интерфейса поздно начинается worker; затем посетитель заново выполняет авторские расчёты мира, строит растительность, готовит GPU и ещё ждёт проявления canvas. HTTP-кэш убирает передачу, но не эти вычисления. Предыдущая v618 уменьшила стартовую передачу desktop, однако почти не затронула главные расчёты и цену кадра.

В этом аудите отдельно подтверждены два небольших резерва без изменения сцены: сокращение проявления даёт **442–479 ms**, ранний запрос двух критичных ресурсов — около **350 ms** на проверенных сетевых профилях. Их эффекты нельзя складывать в обещание до совместного теста. Загрузку до 1–2 секунд и FPS ×2 этим не доказали.

## Свежая публичная загрузка

Chromium 153, ANGLE Metal, Apple M3 Pro. Два холодных контекста на профиль, после каждого обычная перезагрузка с HTTP-кэшем; нормальная текущая сеть без ограничения. Мобильный размер — эмуляция на Mac, не телефон. Готовность означает сообщение worker + класс is-ready; полное проявление — CSS opacity ≥0.98, не подтверждение показа первого кадра дисплеем.

| Профиль | Готовность 3D, холодный | Полностью проявилась, холодный | Полностью проявилась, HTTP-кэш |
|---|---:|---:|---:|
| 1440×900 | 3.90–4.52 s | **4.53–5.14 s** | **3.49–3.60 s** |
| 390×844 | 3.07–3.29 s | **3.68–3.90 s** | **2.88–2.90 s** |

На desktop worker создаётся только на 0.60–1.06 s; init приходит на 0.82–1.39 s. Последний ресурс уже получен за **1.94–1.99 s до готовности** сцены. На мобильном размере этот остаток 1.09–1.25 s. В прогретых запусках Resource Timing показывает нулевую сетевую передачу ресурсов, но desktop продолжает строить мир около трёх секунд. Нельзя списать это на хостинг.

Первая передача ресурсов, без HTML: около 3.66 MB desktop /3.00 MB mobile. Тексты и постер появляются раньше, они не являются готовой живой сценой. На канале 4 Mbit/s передать 3 MB требует около **6 s только по объёму**, ещё без задержек и вычислений. Для первого полноценного вида за 2 s на таком канале нужно существенно уменьшить именно обязательные первые байты, а не только ускорить JS.

Источники: `evidence/c7-v618-startup-fps-audit-2026-11-02/public-path.mjs`, `public-path.json`. Resource Timing worker пересчитан через timeOrigin. Небольшие аномалии начала resource timing worker-entry не использованы для определения границ готовности.

## Что делает worker до первого кадра

Новый диагностический bundle собран штатным упаковщиком из изолированной копии текущих исходников. Добавлены только метки вокруг существующих этапов. Реальный lifecycle worker и зависимости сохранены. Четыре последовательных запуска на размер, локальная сеть; это средние wall spans с перекрывающейся асинхронной работой, **не исключительные доли CPU/GPU**.

| Этап | 390 | 1440 |
|---|---:|---:|
| Импорт мира, включая исполнение top-level terrain | 812 ms | **784 ms** |
| Получение/декодирование/адаптация рельефа и UV | 353 ms | **386 ms** |
| Построение деревьев | 227 ms | **340 ms** |
| Построение ближней травы | 296 ms | **659 ms** |
| Статические GPU-поля травы | 23 ms | 60 ms |
| Дальняя трава | 25 ms | 68 ms |
| Позднее декодирование horizon-полей | 84 ms | 92 ms |
| Загрузка подготовленных текстур в GPU + yield | 26 ms | 36 ms |
| Начальная установка света | 38 ms | 49 ms |
| compileAsync | 50 ms | 55 ms |
| Первый draw: CPU submission и возможные ожидания драйвера | 104 ms | 120 ms |

Импорт — не только чтение 240 KB сжатого JS: `terrain.js` содержит top-level await построения SDF, строк профилей и скульптурных полей. Существующий terrain-cache сохраняет регулярную сетку **до** адаптивного разбиения. Поэтому успешная загрузка кэша не убирает ни все авторские поля, ни адаптацию. Упаковщик соединяет модули, но не отменяет их исполнение.

Desktop строит **1 215 418** ближних травинок; в измеренном начальном main-виде активно около **205 138**. Mobile: 227 547 /16 578. Эти различия показывают резерв для подготовки мира по областям, но не разрешают просто удалить невидимое: другие области нужны отражению, следующим позициям камеры и теням. Создание первого вида и готовность всего пролёта сейчас связаны одним барьером.

Текстуры деревьев/неба начинают запрашиваться лишь внутри фабрики после дорогого импорта: в свежем публичном desktop-прогоне примерно на 1.79 s. В конце фабрики ожидание image-ready уже нулевое, поэтому перенести эти запросы раньше — не то же самое, что сэкономить всё их время. Общая критическая цепочка важнее одной ранней даты fetch.

Не следует снова объявлять compileAsync, перенос в worker или per-texture yield новыми решениями: первые два уже реализованы, множественные timeout на текстуры ранее убраны. Текущий комментарий про yield на каждую текстуру устарел; фактический код делает один yield.

Источники: `worker-stages.json`, `instrumented-source/world.js`, `instrumented-source/worker-entry.js`. Основной код: `lab/c7-scene/world.js`, `terrain.js`, `terrain-cache.js`, `grass.js`; UI: `app/c7/landscape.tsx`, `scene/render-worker.ts`, `scene/shared-world.ts`.

## Два проверенных небольших улучшения

### 1. Проявление 650 →150 ms

Изолированная CSS-подмена в HTML, ABBA, одинаковая сцена. Интервал ready →opacity ≥0.98:

| Размер | Сейчас | Диагностический вариант | Экономия проявления |
|---|---:|---:|---:|
| 1440 | 632.7 ms | 153.9 ms | **478.8 ms** |
| 390 | 606.4 ms | 164.3 ms | **442.2 ms** |

Это ускоряет видимость уже готовой картинки, не расчёты и не FPS. Общий mobile startup кандидата немного шумел; поэтому экономия посчитана по самому интервалу проявления, а не приписана CPU. Изменяется длительность перехода постер→canvas, не качество материалов/геометрии. До выпуска нужна проверка перехода и reduced-motion; полный визуальный regression здесь не запускался.

Место: `app/c7/c7.css`, правила canvas/fallback около строк 99–115. Прототип сохранён в audit `server.mjs`, параметр `?fade=150`.

### 2. Запрашивать world.js и geometry.bin.gz из HTML раньше гидратации

Изолированный `<link rel=preload as=fetch crossorigin>`, ABBA, HTTP cache max-age600 как у текущего Pages. 100 ms задержка, 10 Mbit/s desktop /4 Mbit/s mobile, без CPU throttling.

| Размер | Ready сейчас | С ранним запросом | Выигрыш |
|---|---:|---:|---:|
| 1440 | 4517.4 ms | 4167.6 ms | **349.8 ms /7.7%** |
| 390 | 7109.7 ms | 6757.8 ms | **351.9 ms /4.9%** |

Передача ресурсов одинакова в обеих ветках: 3 658 544 /3 001 945 B. Два тела оплачены в main, worker получает их с transferSize=0; повторной передачи этих тел в тесте нет. Однако desktop выдаёт реальные предупреждения об unused preload из документа: потребитель находится в другом realm, и проверен только Chromium. Это **обоснованный кандидат, не готовый выпуск**. Нужно корректно связать раннюю загрузку с worker, проверить reuse в Firefox/WebKit и ветки Save-Data/без WebGL; затем проверить совмещение с коротким fade. Не следует заранее загружать весь сайт и нарушать принятый terrain-first приоритет.

Доказательства: `early-preload.mjs/json`. Подход соответствует назначению [preload для поздно обнаруживаемых ресурсов](https://web.dev/articles/preload-critical-assets); документация отдельно рекомендует использовать его избирательно.

## Почему проседает FPS

Свежий последовательный 20-секундный пролёт вниз/вверх на каждый размер, 2 s подготовки. Дополнительных GPU waits нет: наблюдались существующие fences и сообщения worker. Закрытые непрозрачным UI интервалы исключены. Добавлены малые счётчики frame work. Это **наблюдаемая скорость завершения GPU-команд**, не rAF и не подтверждённые дисплеем FPS. Один инвентаризационный прогон на размер, не сравнение улучшения версии.

| Размер | Реальный canvas | Завершений/с | p95 интервала frame-сообщений | Среднее вызовов рисования/кадр |
|---|---:|---:|---:|---:|
| 390×844 | 390×844 | **60.0** | 21.9 ms | 753 |
| 1440×900 | 2160×1350 | **37.8** | 81.3 ms | 1478 |
| 2560×1440 | 3840×2160 | **27.2** | 110.2 ms | 1676 |

1. **Фиксированное desktop supersampling1.5.** Даже при deviceDPR1 основной буфер имеет в 2.25 раза больше пикселей. На 2560 это 8.29 млн пикселей, то есть 4K. Снижение до DPR1 было бы изменением качества, а не бесплатной оптимизацией; на Retina оценка нужного разрешения другая. Никакое разрешение в продукте не изменено.
2. **Дорогой динамический свет и многократная отрисовка мира.** Sun +3 sky lights имеют 4096² desktop/2048² mobile shadow maps. Три rear-fill карты уже статические, их нельзя записывать в постоянно обновляемые. К этому добавляются tree atlas, PMREM, отражение и main render. На изменившемся солнце desktop отправляет в среднем 8.78 млн triangles во все проходы вместе; на wide9.26 млн, максимум всего кадра9.92 млн. Это повторная работа над геометрией, не количество уникальных треугольников мира.
3. **Много небольших draws.** Сохранение мелких patches помогает отсекать невидимую траву, но обход/отправка полного кадра занимает в среднем 7.9 ms desktop /9.3 ms wide, а в кадрах со сменой света12.0/13.4 ms. Это CPU submission wall time, включая возможные driver stalls, не чистое GPU время. Пик wide2611 calls. Просто склеить patches нельзя: прежний эксперимент ухудшил culling.
4. **Стоимость шейдеров сохраняется и без обновления света.** PCF, horizon-поля, деревья, два разных слоя отражения света травяного покрова всё равно участвуют в затенении видимых пикселей. Остановка setLight не отменяет стоимость sampling. Полный вклад каждого GPU-pass отдельно не измерен, проценты «GPU тратит X% на тени» не выдаются.

Важное исправление старого аудита v615: квантование солнца 1/256 **уже есть**. В текущем пролёте свет обновлялся в33.3% desktop /40.5% wide кадров; отражение — в38.5%/44.5%. Утверждение «всё это на каждом кадре» теперь неверно. Часть пути reflection уже пропускается по консервативной occlusion-проверке. Реальные потенциальные выигрыши меньше, чем при чтении устаревшего отчёта.

Источники: `flight-inventory.mjs/json`, `world.js:253,313,375`, `sky-light.js`, `rear-fill.js`, `lake.js`, `sky-horizon.js`. [WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices) различает batching, blocking calls и уменьшение буфера как компромисс качества. `compileAsync` и размеры буфера описаны в [WebGLRenderer](https://threejs.org/docs/pages/WebGLRenderer.html). Онлайн API не подменяет проверку закреплённой в проекте Three r186.

## Что не стоит делать

**Не экспортировать все готовые массивы прямо в сетевой пакет.** Новый диагностический размер существующих typed arrays, с устранением повторных одинаковых views и обычным gzip:

| Группа | Mobile gzip | Desktop gzip |
|---|---:|---:|
| Ground, включая дочернюю геометрию | 12.35 MB | 12.35 MB |
| Деревья | 8.18 MB | 16.61 MB |
| Ближняя трава | **11.02 MB** | **58.32 MB** |
| Дальняя трава | 2.11 MB | 10.28 MB |

Это не окончательный кодек, не нижняя граница возможного сжатия и не готовый формат: метаданные/materials/bounds не включены. Но этого достаточно, чтобы отвергнуть совет «просто сохранить весь построенный мир в GLB/бинарник» без расчёта передачи. Небольшие детерминированные параметры и локальный кэш могут быть полезнее полной выгрузки массивов. Источник: `cache-size-probe.mjs/json`; продукт/данные посетителя не изменялись.

Не повторять без нового основания S6 consumer cache: прежний прирост3.65–5.44% не прошёл gate. Не повторять наугад уменьшение деревьев, теней, отражения, плотности или DPR; ранее отклонённые radiance/depth passes, объединение grass patches и shadow scissor не становятся решениями после нового названия. Не считать удаление старых runtime из репозитория ускорением посетителя — они уже не входят в текущий HTTP-путь. Не обещать ×2 от ещё одного worker или смены хостинга.

## Следующий план реализации без потери принятой картинки

1. **Короткий переход + ранняя передача.** Довести два проверенных выше кандидата до одного изменения. Проверить фактическое повторное использование fetch в трёх движках, reduced-motion/fallback/abort и отсутствие повторных байтов. Приёмка — ABBA normal/10Mbps/4Mbps и одинаковые фиксированные кадры. Выигрыш каждого кандидата измерен отдельно; общий пока не измерен.
2. **Развязать первый живой вид и строительство всех областей.** Составить точный набор первого main/reflection/shadow вида с запасом для скролла; строить оставшуюся near-grass область после первого кадра. Сохранять seeds, root attributes, LOD и порядок для каждой patch. Проверить быстрый скролл и прямые якоря: не допускаются пустая земля, pop-in или недостающие отражения. Это новый архитектурный прототип, не прежний S6; потенциально устраняется часть участка659 ms, но не обещаются все659 ms и тем более все4 s. До изменения генератора измерить долю обязательных patches во всех проходах.
3. **Убрать ненужное авторское построение на успешном пути.** Разделить terrain authoring/runtime и точечно сохранять компактные результаты оставшихся потребителей. Начать с выявленных784 ms импорта и386 ms подготовки рельефа; не добавлять многомегабайтный переносимый кэш. Новый формат допускается только после общего cold-start сравнения, учитывающего сеть, decode и SHA. Старый S6 без нового формата/причины остаётся NO_GO.
4. **Отдельно ускорить повторный визит.** Прототип versioned cache конечных данных в IndexedDB после появления сцены, с лимитом, проверкой версии и процедурным fallback. Это не ускорение первого визита; крупные случайные массивы не сохранять без теста цены записи/чтения. [IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API) подходит для структурированных локальных данных, но наличие API не доказывает выигрыш здесь.
5. **FPS: один узкий прототип сокращения draws с прежним culling.** На проверенном Chromium доступен WEBGL_multi_draw. Исследовать общий storage + список тех же видимых patch/density/LOD для каждого прохода, не укрупнять область culling. Instanced grass не заменяется одной строкой на BatchedMesh: нужен корректный per-draw диапазон экземпляров, прежний порядок и fallback без расширения. Pixel gate перед полноценным пролётом. Это уменьшает submission, но не цену fragment shader или число triangles; ×2 заранее не обещать. [WEBGL_multi_draw](https://developer.mozilla.org/en-US/docs/Web/API/WEBGL_multi_draw) имеет неполную межбраузерную доступность; [BatchedMesh](https://threejs.org/docs/pages/BatchedMesh.html) — справка о возможностях, не доказанный готовый адаптер для этой травы.
6. **После каждого принятого изменения один целевой regression; один общий выпуск в конце.** 390/1440/2560, dawn/noon/sunset/contact, обратный ход, ready vs fully-visible отдельно, фактические GPU completions, отсутствие новых HTTP-тел и память. При отсутствии измеримого выигрыша или при ухудшении изображения — отклонить. Цель40–60 FPS остаётся прежней.

Именно пункты2–3 меняют архитектуру ожидания, а5 — работу кадра. Быстрые пункты1 полезны, но сами по себе не обеспечивают ни первый полный мир за1–2 s на4Mbps, ни двукратный FPS.

**NOT_RUN:** физические iOS/Android, слабый GPU, настоящий Safari, экранные дикторы, presented FPS, точная GPU-разбивка по проходам, приёмка визуального соответствия image3, совместный выпуск кандидатов. Сайт не обновлялся; его актуальная версия остаётся v618. Сводка чисел — `evidence/c7-v618-startup-fps-audit-2026-11-02/summary.json`; сохранность — `preservation.json`.
