### Что уже установлено — не трать время на повтор

Uniform-ветка для пропуска fragment shading сама влияла на скорость; её25/9/4%для ground/near/far не считать долями GPU-времени. Перестановка grass colour перед terrain colour оказалась на5,7%дороже и изменила пиксели; не повторять. Старые GPU query признаны недостоверными.

### Порядок работы

**1. Зафиксируй сравнение,30–45мин.** Сохрани SHA baseline и runtime. Используй `scripts/c7-flight-paired.mjs` с явно заданными URL и новым evidence-каталогом. Разделяй render submissions, активные интервалы rAF, suspension и completed-batch wall time. `environmentCalls` включает atlas, а `reflectionCalls` может включать обновление shadow maps: поправь подписи/границы измерений, не приписывай им исключительные GPU-времена. Не добавляй gl.finish или profiler в продуктовый цикл. Native A/A обязателен; инструментированную скорость не сравнивай с обычной как равные протоколы.

**2. Исправь подтверждённую проблему подготовки,60–90мин.** В `sky-horizon.js` обе загрузки сейчас идут последовательно и не получают AbortSignal. Протяни signal от `createC7Scene`; начни два fetch одновременно, но декодируй последовательно, чтобы ограничить пик. Добавь отмену между chunk/yield декодера и освобождение уже созданной текстуры при ошибке второй. Не меняй decoded данные и последовательность shader installation. Проверь задержку каждой загрузки, ошибку второй, abort во время fetch/decode и SHA восстановленных данных. Это улучшение старта/отмены, не заявляй прирост steady-state FPS.

**3. Для FPS выбери один архитектурный прототип.** Основной путь — замена повторного low-sky transport, без нового runtime radiance FBO. В первые2часа подготовь точный контракт: для ground surface и raised canopy получить отдельную видимость/падающую энергию каждого из3sky sources при текущем solar; сохранить альбедо, микронормали, view-dependent BRDF, солнце и контактные тени. Укажи `старый расчёт → замена → receivers → удаляемые ресурсы → ошибка → байты`.

Кандидат: offline коэффициенты переноса статической геометрии вдоль solar-path, адаптивно уточняемые у границ видимости. Runtime восстанавливает коэффициенты, материал считает оставшуюся физику. Сначала сделай небольшой участок земли **на границе тени**, включая зеркальную камеру и промежуточные solar-фазы. Это исследование допустимого представления, не заранее разрешённое ухудшение картинки.

Не интерполируй готовую visibility как будто это эквивалентно интерполяции horizon angle перед нелинейным asin. Не объединяй разные источники в одну маску. Не запекай готовый цвет с направлением взгляда. Новый формат должен заменять старую работу и укладываться в заранее записанные суммарные CPU/GPU/HTTP бюджеты. Перечисли всех потребителей: земля, обе травы, листья, кора. Нельзя обещать убрать3карты, пока деревья нуждаются в них. Если все старые проходы остаются и сверху появляется cache — останови этот кандидат.

На первый прототип закладывай8–16часов; полный переход может занять несколько дней. Это оценка сложности, не разрешение бесконечно экспериментировать. После2часов без конкретного удаляемого расхода — no-go с доказательствами. После прототипа ориентир продолжения —≥15%снижения стоимости в native-проверке и согласованный выигрыш полного сайта без видимого ухудшения. Это порог окупаемости сложности, не обещанный результат. При2–3%или росте памяти/старта новый формат не интегрируй. Не заменяй неудачу двадцатью новыми гипотезами.

**4. Память и старт проверяй отдельно.** `grass-static.js` запрашивает около116,7МБ временных CPU+GL буферов normal, затем синхронный getBufferSubData; retained дополнительные атрибуты≈9,72МБна каждой стороне CPU/GPU. Это модель выделений, не measured resident peak. Сначала измерь cold start и длительность подготовки normal/low. Если цена существенна, готовь ограниченными чанками с yield/signal, сохраняя GPU-математику и CPU-копии для восстановления. Не менять вычисления на CPU sin/cos без доказательства равенства. Не отменять TF целиком без парного сравнения скорости, старта и памяти.

**5. Интегрируй только прошедший кандидат.** Пакетируй через `scripts/c7-package-world.mjs`, затем перенеси реальный runtime в out с новым manifest. Native-stage возможен только при доказанно неизменном UI/static export и явном allowlist; иначе новый Next build. Не оставляй результат только в lab. При изменениях terrain/adaptive geometry пересоздай связанные terrain/sky caches; metadata left-cache обновлять только после нового доказательства неизменности данных.

### Критерии приёмки

- Native A/A, затем B/C/C/B и C/B/B/C, прогрев полного маршрута, одинаковые viewport390/1440/2560,DPR,quality,позы и время. Для основного сравнения≥30секунд, raw intervals и разброс сохранить. Новые ошибки/компиляции во время steady-state объяснить до принятия.
- Полный сайт измерять отдельно от непрерывной сцены. State.frames — submissions. Контролируемое завершение GPU — отдельный benchmark. Не называть их displayed FPS.
- ×2от v598/1440 означает≥32,08в его протоколе; от текущей длинной v599≈33,14. Сравнивать свежие одинаковые протоколы. Цель40–60из ТЗ не отменяется. На390 нельзя обещать65показанных FPS на60Гц: проверять половину стоимости одинаковой работы и реальную плавность устройства.
- Открыть reference `screenshots/c7/2026-10-24-reference-rebuild-exec081/source/image3.jpg` и v599-кадры. Для performance-регрессии baseline — v599, не другое время/кроп reference. Проверить33позы, оба направления, низкое солнце, ROI берега/крон/теней, отражение на нескольких wave-times. Средний diff по экрану не скрывает локальный дефект; tolerance не равен художественному разрешению.
- Context loss/restore,dispose,abort; актуальные функциональные наборы и Chromium/Firefox/WebKit. Headless WebKit не заменяет native Safari. Все исходные FAIL сохранять.
- Сеть измерять HTTP encoded cold отдельно от ZIP/raw/cache. Mobile3–6МБ/desktop5–10МБ остаются целями; отложенная загрузка не должна портить первый кадр или быстрый пролёт.

Физические iOS/Android, слабый GPU, native Safari,VoiceOver/TalkBack при отсутствии устройств пометить NOT_RUN. Не повышать G04/G07из REWORK или G08из OPEN без новых доказательств. Хостинг и отложенное закрепление владельцем не блокируют локальную работу; не спрашивай их снова.

В конце выдай: конкретный diff, что ускорилось и по какому протоколу, цена памяти/старта/передачи, все отвергнутые кандидаты с причиной, просмотренные кадры, локальный проверенный пакет при наличии принятого изменения и оставшиеся NOT_RUN. Если крупное ускорение не получилось — прямо скажи это; не публикуй и не объявляй задачу40–60FPS выполненной. Принятое исправление старта можно сдать отдельно с честным названием результата.
