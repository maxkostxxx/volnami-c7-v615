# C7 после v614: память построения деревьев, L0

Подтверждено избыточное для текущего runtime удержание CPU-данных генератора: готовые 13 деревьев хранят исходные JS-массивы и процедурный каркас рядом с уже скопированной BufferGeometry. В отдельном Node-процессе освобождение трёх ссылок уменьшило стабилизированный JS heap на **86,00 МиБ desktop** и **53,19 МиБ mobile**. Это новый диагностический результат; в опубликованном v614 эти данные ещё сохраняются.

Это не доказанное ускорение кадров и не resident GPU memory. Снятие давления с памяти может помочь слабым устройствам, но частота GC, паузы, время запуска и поведение физического телефона здесь не измерялись. Удержание данных имеет смысл в редакторе деревьев; дефектом является их ненужное время жизни в неизменяемом C7 runtime, а не само существование генератора.

## Причина и владельцы

`lab/c7-scene/vendor/ez-tree/tree.js:131` и `:169` сохраняют `branches`/`leaves` после meshing; `:248` сохраняет `skeleton`. `createBranchesGeometry()` и `createLeavesGeometry()` копируют числовые массивы в типизированные атрибуты, поэтому исходные массивы продолжают занимать отдельную память. Текущий `trees.js:714–844` строит дерево один раз, меняет готовые атрибуты, фиксирует stats и добавляет его в сцену. Последующие solar/environment-обновления обращаются к материалам, координатам и bounds, но не к исходным массивам.

Дерево остаётся владельцем этих данных. Кроме scene graph и crowns, его удерживает closure `onBeforeCompile` из `tree.js:935`, читающий `this.options.leaves.roundedNormals`. Просто заменить Tree на Group недостаточно: closure сохранит исходный объект. Освобождать готовую BufferGeometry нельзя — её используют основной рендер, тени, reflection и восстановление контекста.

## Протокол и данные

До теста записан `evidence/c7-architecture-speed-2026-10-31/l0-tree-retention-hypothesis.json`. Один свежий Node24.1.0 процесс на профиль, настоящие13 placements, декодированный текущий terrain и настоящий sampler, Texture-заглушки без GPU/загрузки изображений. Процессный `--expose-gc` не меняет окружение других процессов. Два стабилизированных memory sample до и после удаления только `branches`, `leaves`, `skeleton`; результат — разность вторых sample. Продуктовые файлы не менялись.

Число объектов — объяснение удержания, не диагноз GPU-стоимости. RSS изменился иначе: он включает процесс целиком и поведение аллокатора. ArrayBuffers/external/heapUsed не складываются без учёта пересечения категорий. [Документация Node24.1.0](https://nodejs.org/download/release/v24.1.0/docs/api/process.html#processmemoryusage) определяет эти поля. [Документация Three](https://threejs.org/manual/pages/how-to-dispose-of-objects.html) отдельно описывает освобождение GPU-ресурсов; в этом опыте `geometry.dispose()` до измерения не вызывался.

Порог ≥8 МиБ в обоих профилях пройден, raw-buffer alias с геометрией не найден. Однако прямое обнуление сломало getters `vertexCount`/`triangleCount` на всех13 деревьях. Такой вариант **не является готовой правкой**. Исходные данные: `l0-tree-retention.mjs`, `l0-tree-retention-{full,mobile}.{json,log}`. Одного процесса на профиль достаточно для проверки порядка размера, но это не доверительный интервал browser heap или пауз GC.

## L1: следующий исполнимый шаг

1. Добавить в evidence-кандидат явное освобождение данных построения после окончательной обработки геометрии. Включать его только для runtime; обычное редактирование/генерация по умолчанию должны сохранять прежнее поведение. Не менять алгоритм дерева или количество вершин.
2. Сохранить getters количества вершин/треугольников по готовой геометрии. Явно определить контракт новых post-release вызовов: `generate()`/`generateLODs()` восстанавливают данные; `createGeometry()` умеет вновь построить skeleton. Методы прямого remesh из старых buffers не должны молча менять форму или падать случайным TypeError. Требуется осмысленный guard/документация нового opt-in жизненного цикла.
3. CPU-проверка всех13 placements ×2профиля: все атрибуты/индексы/bounds/matrices/stats/materials точны; освобождение повторяемо; счётчики и повторная генерация работают; отмена/очистка не оставляют владельцев. Повторить memory gate уже на безопасном кандидате.
4. Только после CPU gate — короткая headless проверка fixed poses обоих профилей, контекст loss/restore и отмена. Отдельно измерить browser-worker JS heap доступным методом без постоянной instrumentation в продукте. Не заявлять точный resident GPU peak.
5. Перед интеграцией проверить влияние на запуск в парном тесте и отсутствие ухудшения стоимости кадра. Не требовать от memory fix вымышленного FPS-ускорения; приёмка — значительное удаление CPU retention с неизменной картинкой и корректным жизненным циклом.

Terrain/sky cache data от времени жизни CPU-массивов не зависят. При изменении trees/vendor source нужно заново проверить source-provenance manifests, bundle SHA и производные mobile-ресурсы установленным workflow; не принимать старый manifest только потому, что картинка ожидается прежней. Чистый v614 checkpoint/ZIP уже сохранён.

## NOT_RUN

Безопасный L1-кандидат, продуктовая интеграция, новый runtime-пакет, browser heap, частота/паузы GC, GPU pixels, новая скорость загрузки/кадра, native Safari, физические iOS/Android и слабый GPU **не проверялись в L0**. G04/G07REWORK, G08OPEN. Адаптивный DPR остаётся отдельным вопросом требований, не предпосылкой этой работы.

Прочитаны: текущие vendor `tree.js` (generate/generateLODs/createGeometry, создание материалов/геометрий, getters), `trees.js` (построение и обновление), строка вызова в `world.js`, `vendor/ez-tree/PROVENANCE.md`, CPU fixture `i4-cpu-parity.mjs`, текущие C7 consumers через `rg`, две первичные страницы документации выше. Страница Three по старому `/manual/en/` URL вернула404; использован найденный действующий `/manual/pages/` URL. Старый PROVENANCE описывает состояние исходного импорта и не доказывает отсутствие последующих локальных изменений алгоритма; перед правкой vendor его следует согласовать с фактическим diff.

## L1: безопасный evidence-кандидат, следующий проход

Предыдущий проход классифицирован как progress: v614 опубликован, L0 изменил следующий шаг. В начале нового прохода97checkpoint SHA, ZIP и пользовательский diff снова совпали. Реализация пока находится только в `evidence/c7-architecture-speed-2026-10-31/l1-source/`.

Выбран локальный подкласс `RuntimeTree`, а не правка vendor. Обычный `Tree` и его authoring-поведение остаются прежними. Новый opt-in `releaseConstructionData:true` выбирает подкласс; после окончательной геометрии и stats каждого дерева освобождаются три ссылки. Getters после release читают числа из готовых атрибутов/индексов. `generate()`, `generateLODs()` и `createGeometry()` восстанавливают нужные данные. Прямое пересоздание geometry из уже удалённых исходных массивов сообщает ясную ошибку **до** dispose живых ресурсов. Это явно документированный контракт нового opt-in, не незаметная смена поведения обычного генератора.

CPU gate прошёл:13реальных trees×2профиля дают exact атрибуты, индексы, bounds, matrices, stats, getters и material hooks. На всех26 проверены повторный release, guards без dispose, повторная генерация и `createGeometry()` против исходного vendor. Два claimed-handle abort-сценария очищают ресурсы ровно один раз. Готовность изображений всё ещё может быть pending во время построения.

В первоначальном CPU fixture ошибочно ожидалось0dispose при заранее отменённом сигнале, хотя сам mock `takeForBuild()` безусловно передавал владение. Фабрика правильно сделала1dispose. Исправлено ожидание mock-контракта; исходный протокол/лог сохранены. Это не исправление продуктового поведения (`l1-cpu-protocol-correction.json`).

Четыре изолированных Node-процесса — baseline/candidate каждого профиля — подтвердили уже на безопасной реализации: desktop heap160 427 928→70 237 968B (**−86,01МиБ**), mobile126 014 640→71 102 832B (**−52,37МиБ**). Геометрия и getters точны; у candidate исходных массивов/каркасов0. Это отдельный опыт, не повторное название результата L0. Источники: `l1-cpu-parity.json`, `l1-memory-{full,mobile}-{baseline,candidate}.json`, `l1-memory-decision.json`.

Прочитаны определения в установленном `node_modules/playwright-core/types/protocol.d.ts` и первичные страницы [Runtime](https://chromedevtools.github.io/devtools-protocol/tot/Runtime/), [HeapProfiler](https://chromedevtools.github.io/devtools-protocol/tot/HeapProfiler/), [Target](https://chromedevtools.github.io/devtools-protocol/tot/Target/). Первый браузерный опыт остановлен после обнаружения второго фактора: diagnostic bundle использовал исходные Three-модули, а production — те же модули после установленного предварительного minify.
