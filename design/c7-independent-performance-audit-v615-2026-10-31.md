## Короткий вердикт

**Старт.** Ограничен тремя вещами: (1) цепочка «гидратация → worker → world.js 836 КБ» не начинается до исполнения клиентских чанков; (2) два крупнейших тела — `world.js` (836 КБ) и `terrain-cache/geometry.bin.gz` (942 КБ) — обязательны для всех профилей и уже максимально компактны в текущем контракте (T1-кодек, −36% к предыдущему); (3) финальный барьер текстур + `initTexture` по одной + `compileAsync` + первый `setLight` стоят строго в конце. Контролируемая готовность живого 3D по истории: 3.28–4.88 с на 10 Мбит/с/100 мс (v612–v615); локально без сети у меня: 2.97 с mobile / 3.40 с desktop. Первый контент (постер, текст) — сотни миллисекунд, это уже достигнуто и отделено от готовности 3D.

**Кадр.** Ограничен тем, что прокрутка во время travel меняет solar непрерывно, а `setLight` (PMREM из сцены + tree-atlas 1024×4096 + `shadowMap.needsUpdate` для 4×4096² + 3×2048² карт) вызывается на каждое изменение solar, т.е. практически каждый отправленный кадр; движение камеры дополнительно делает dirty отражение → полный reflection-проход всей сцены в HDR MSAA-таргет каждые кадр. На M3 Pro 1440×900: ~42 submitted/с, mobile 390: ~60.5 submitted/с. На слабом десктопе/телефоне это даёт видимые рывки (G07 открыт). Отдельная дисплейная стоимость подтверждена историческим D5: −27.5% времени пакета при четверти main raster coverage.

**Память.** v615 освободила JS-heap worker по-настоящему (38.1/65.3 МиБ после диагностического GC) — это экономия CPU-памяти, не GPU. Геометрические ArrayBuffers (terrain ~25 МБ, деревья 14.6/29.5 МБ), текстуры и GPU-resources не уменьшены; resident GPU peak не измерен (NOT_RUN). Принудительный GC не доказывает уменьшения естественных пауз.

**Где измерений недостаточно.** Пофазные CPU-доли старта (декод terrain 942 КБ gz → 17.1 МБ payload, адаптивная тесселяция, деревья, ближняя/дальняя трава, декод horizon полей в конце) на v615 не инструментированы; единственный прежний срез (s1, ~720 мс модуля из прошлой архитектуры) устарел. Presented FPS и реальная плавность физических устройств по-прежнему NOT_RUN.

## Карта кадра

`scroll` → `exactProgress` → демпфирование `1-exp(-14.4*dt)` (`landscape.tsx:177`) → `world.render(progress,time)` (главный поток, только сообщение) → worker: `pending`+`pump()` → `renderState` → `solarForTravel(progress)=progress` для progress<0.83 → `lastSolar!==solar` → **`setLight()` на каждый такой кадр** (`world.js:371`), внутри: `atmosphere.update`, `skyLight.update`, `rearFill.update`, `fitWorldShadows`, `skyHorizon.update` (перерисовка tree-atlas 1024×4096), `trees.updateLighting`, **`pmrem.fromScene` (128-куб + фильтр)**, `shadowMap.needsUpdate=true` (регенерация 4×4096² + 3×2048² внутри ближайшего render) → камера двигалась → `dirty` → **`lake.reflect`** (полный рендер всей сцены из зеркальной камеры в HDR MSAA-таргет, `lake.js:149–170`) → `renderer.render(scene,camera)` (main) → `fenceSync` → `postMessage('frame')`. Очередь ≤3 fences, приостановка `setActive(false)` при покрытии непрозрачными секциями/скрытой вкладке/reduced-motion — работает (K0, код worker-entry).

Фактически прокруточный кадр = shadow-регенерация + atlas + PMREM + reflection-проход + main-проход. Это подтверждает и объясняет «рывки» на слабых устройствах без всяких допущений о GPU-профилях.

## Восемь главных проблем

1. **Solar-зависимый `setLight` на каждый прокруточный кадр** — подтверждённый расход; необходимость оценить. `world.js:371` + `:245–281`. Механизм: PMREM+atlas+shadows на каждый кадр во время travel (solar меняется непрерывно). Кандидат: квантование solar-фазы для света (например, шаг 1/256) с сохранением плавности камеры — свет меняется дискретно, но 256 состояний на цикл визуально плавны. Риск: отступление от «точного» контракта освещения, требуется pixel-пороговая приёмка и согласование по качеству. Стоимость: малая (одна строка + тест). Приёмка: pixel-пары по 20+ фазам, ABBA-пакет, отсутствие видимых ступеней заката. **Не заменяет** работу над самими проходами.
2. **Desktop холодный старт +835 КБ case-картинок** — подтверждённый расход (N2). Файлы: `cases/c7/extra-meat/example3.webp` 590 КБ (672×900), `cases/c7/hobby-games/poster.jpg` 244 КБ. Механизм: lazy-маржевое поведение Chromium. Исправление: `fetchPriority="low"` на эти изображения + пережатие example3.webp (визуальная сверка обязательна). Ожидаемая польза: разгрузка канала на старте desktop. Риск: только если пережатие изменит вид — контроль по текущему экрану. Стоимость: 30–60 мин. Приёмка: request-map повторно (нет картинок до скролла).
3. **Два крупнейших тела неразделимы между профилями** — подтверждённый расход, необходимость оценить: `world.js` 836 КБ (Brotli на CDN ~260–300 КБ) и `terrain-cache/geometry.bin.gz` 942 КБ (бинарь, не сжимается). История: S6 (~110 КБ consumer-данных) дала 3.65–5.44% — NO_GO; T1 уже взят. Дальнейший выигрыш — только смена контракта точности (недопустимо без решения) или code-split runtime (перенос трёх.js отдельно — экономия повторной передачи у повторных визитов, не у холодного).
4. **Декод horizon-полей стоит в конце и на том же потоке** — обоснованная гипотеза: `world.js:219` после всех построений; в v615 доли не измерены. Механизм: worker-CPU серийно. Вариант: декодировать в отдельном потоке/на main thread во время CPU-построений (перенос работы, не её удаление; параллельность возможна, т.к. главный поток простаивает). Сначала — инструментировать стадии (30–60 мин), решение — по цифрам.
5. **Финальный барьер: текстуры → upload → compileAsync → первый setLight — последовательные CPU+GPU-этапы в самом конце** — подтверждённая структура, доли без измерений. `world.js:417–436`. Часть уже перекрыта (v613 I4), остаток — предмет того же инструментирования, что и (4).
6. **Кумулятивный CPU в одном worker: terrain decode/adapt + деревья + трава + far-grass + static-prep (TF+readback!) + horizon декод** — подтверждённая структура; `grass-static.js` использует `getBufferSubData` (синхронный readback) в батчах с yield. Обоснованная гипотеза: это основной вклад локальных 2.97/3.40 с. Не «архитектурная ошибка», а осознанный монолит; требует замеров перед действиями.
7. **Desktop raster: DPR 1.5 → 2160×1350** — подтверждённый крупный расход по истории (D5: −27.5% пакета при 25% main coverage; диагностика, не продукт). Адаптивный desktop-разрешающий режим — вопрос требований (не разрешён), в отчёте истории так и остался «без ответа». Исправление возможно только после решения пользователя; механизм пользы: меньше фрагментов главного прохода при сохранении резкости ближнего плана через опцию.
8. **Публичный хостинг harvis.page нестабилен для части российских сетей** — подтверждённый факт (см. раздел «Доступ»). Отдельно от производительности 3D; на месте перенесено на GitHub Pages (временное решение, G08 остаётся OPEN до проверок из домашних сетей РФ).

## Один основной путь ускорения

По фактам (D5 — единственный измеренный крупный рычаг кадра; история кадровых кандидатов вся NO_GO) самый большой достоверный выигрыш — **адаптивный desktop-режим разрешения** (снижение drawing buffer при движении/на слабых устройствах с сохранением полного качества в покое). Он требует изменения требований (явное решение пользователя) и поэтому формально остаётся рекомендацией, а не планом. Без него большой выигрыш без переработки **не доказан**: все проверенные кадровые кандидаты (H1–H3, J1/J1B, F1, G1, R1, P2, M5) дали <9% или шум. Поэтому основной путь формулирую как **измерить и убрать простои старта (пункты 4–6)** — это единственная область, где история показывает реальные последовательные окна (I1: 0.8 c между модулем и фабрикой; v613: +17–18% от перекрытия текстур), а у меня сейчас нет пофазных цифр. Что исчезает: ожидания на одном потоке; что добавляется: инструментирование и, при подтверждении, перенос декодов; первый кадр не меняется по составу, меняется его задержка; дальнейший пролёт не затрагивается.
